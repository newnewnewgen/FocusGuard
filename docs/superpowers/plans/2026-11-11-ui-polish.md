# UI Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Six app-only changes to the menu-bar app (spec `docs/superpowers/specs/2026-11-11-ui-polish-design.md`): lists can be reordered and the first one is the default a new window attaches to (§6); the "Add window" button becomes a ghost row under the last window (§2); an `info.circle` popover explains the three unlock modes with the real Friction sheet and the real locked controls rendered inline (§1); the Status tab's install/login/keyword rows move into a Setup sheet that appears by itself when protection is not healthy (§3); the uninstall button (§4) and the "Blocked so far" caption (§5) go, with their dead code.

**Architecture:** No daemon, config-schema or lock change. The two pieces of logic that can be wrong get pure functions and tests in the app target: `Config.newWindow()` / `Config.moveLists(fromOffsets:toOffset:)` (`Model/ConfigEdits.swift`) and `SetupNeed.evaluate(_:)` over an `Installer`-independent `Flags` struct (`Model/SetupNeed.swift`). Everything else is SwiftUI: a `GhostWindowRow` and an `UnlockModeHelp` popover in the Schedule tab, a `RemoveButton` view shared between Block Lists and the popover's locked-state preview, `ChallengeSheet(isPreview:)`, and a `SetupSheet` presented from `SettingsView` through one new `AppModel` flag. Reordering lists goes through `model.apply` like every edit; it moves `config.blockLists` and touches no `blockListIDs`, so `weakens(from:)` is nil and the gate never fires.

**Tech Stack:** Swift 5 mode on the 6.2 toolchain, SwiftPM, XCTest, SwiftUI on macOS 15.

**Conventions (same as previous plans):** commit messages end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`. Run `swift test` from the repo root. Nothing in this plan needs `sudo`, the installed daemon, or a password prompt.

**Branch state at execution time:** `chrome-pages` will have been merged into `main` before this plan runs. It adds `AppModel.chromePages: String?` (values `"off"`, `"applied (2 patterns)"`, `"error: …"`, `"not applied …"`, nil when no daemon status), `AppModel.hasChromeURLs`, a "Chrome pages: …" row inside the Status tab's Protection section, and may change the `Section("Now")` "Blocking" line to count Chrome pages. Task 4 says what to do in each case. import SwiftUI

```swift
/// The drop target for the eye under the last window (UI polish spec §2): a dashed outline with
/// a plus and the window it would add, faint until the pointer is over it. With no windows at
/// all it is drawn at full opacity permanently and carries the caption that used to be the
/// empty-state text; with no block list it is disabled and says why.
struct GhostWindowRow: View {
    let caption: String?
    let enabled: Bool
    /// Always fully visible (the empty state) rather than only on hover.
    let permanent: Bool
    let action: () -> Void

    @State private var hovering = false

    var body: some View {
        VStack(alignment: .leading, spacing: 6) {
            Button(action: action) {
                HStack(spacing: 8) {
                    Image(systemName: "plus.circle")
                    Text("New window · Mon–Fri 09:00–12:00")
                    Spacer()
                }
                .foregroundStyle(.secondary)
                .padding(.horizontal, 12)
                .padding(.vertical, 10)
                .frame(maxWidth: .infinity)
                .background(
                    RoundedRectangle(cornerRadius: 8)
                        .strokeBorder(.secondary, style: StrokeStyle(lineWidth: 1, dash: [6, 4]))
                )
                .contentShape(Rectangle())
            }
            .buttonStyle(.plain)
            .disabled(!enabled)
            .accessibilityLabel("Add window")
            if let caption {
                Text(caption).font(.caption).foregroundStyle(.secondary)
            }
        }
        .opacity(permanent || hovering ? 1 : 0.35)
        .animation(.easeInOut(duration: 0.15), value: hovering)
        .onHover { hovering = $0 }
    }
}
```

```swift
/// The `info.circle` popover beside a window's unlock-mode control (UI polish spec §1): one

struct UnlockModeHelp: View {

    /// Ten words from `Challenge.words`, so it looks like a sentence the real sheet would draw.
    static let sampleSentence = "quiet river seven green bottle garden morning silver window travel"
    private static let sampleUntil = TimeOfDay("20:00")!

    init(mode: UnlockMode) {
        _page = State(initialValue: mode)
    }

    var body: some View {
        VStack(alignment: .leading, spacing: 14) {
            Picker("Unlock mode", selection: $page) {
                ForEach(UnlockMode.allCases, id: \.self) { Text($0.title).tag($0) }
```

```swift
import Foundation

/// Whether the Setup sheet must be shown, decided from the installer's four facts alone so it
/// can be tested without an `Installer` (UI polish spec §3, §8).
enum SetupNeed {
    struct Flags: Equatable {
        var daemonInstalled: Bool
        var legacyDaemonRunning: Bool
        var needsUpdate: Bool
        var daemonRunning: Bool
    }

    /// In the order `SetupSheet.daemonRow` tells them: the first that applies is the one shown.
    enum Reason: Equatable {
        case legacyDaemon, notInstalled, needsUpdate, notRunning

        var title: String {
            switch self {
            case .legacyDaemon: return "Protection needs reinstalling"
            case .notInstalled: return "Background daemon not installed"
            case .needsUpdate: return "Background daemon needs updating"
            case .notRunning: return "Background daemon installed but not running"

        }

    static func evaluate(_ f: Flags) -> Reason? {
        if f.legacyDaemonRunning { return .legacyDaemon }
        if !f.daemonInstalled { return .notInstalled }
        if f.needsUpdate { return .needsUpdate }
        if !f.daemonRunning { return .notRunning }
        return nil
    }
}
```

**Ambiguities resolved, and how:**
- *Where the Dock toggle goes.* §3 lists what stays on Status ("notices, Now and nothing else") and names "Dock fallback" among the problems the sheet would show, but does not list the Dock toggle among the sheet's steps. It is on the sheet as a fourth row (green when the icon is on screen or the Dock stand-in is on) so the toggle stays reachable; Status flags it only in the one unreachable state (icon hidden *and* Dock off). The spec's auto-close triggers are the installer flags only; the Dock row never opens the sheet by itself.
- *Auto-close vs "Setup…" from a healthy state.* Closing 1.5 s after "every shown step turns green" would make the login toggle unreachable when the sheet is opened deliberately while healthy, so the close fires only on a transition to green while the sheet is open (`onChange`), never on appear.
- *Keyword step vs keyword problem.* On the sheet the keyword row is green only when `watching …`; on Status it is a problem only when it starts with `error:` ("waiting for network" keeps the sheet open but does not nag on Status). Chrome pages, if present, follow the same split (`applied` green; `error:` / `not applied` a problem), per the chrome-pages notes.
- *Ghost row when windows exist but no list.* §6 only says the no-list caption appears "then"; the caption and the disabled state are tied to `lists.isEmpty` regardless of windows, so the reason is visible whenever the row cannot act. The row is the last `List` row (so it sits under the last `WindowRow` and scrolls with it) rather than a view pinned under the list.
- *"Continue" button and "shield badge".* The real sheet's button is "Unlock" and stays so in preview (spec asks for the real view); `ProtectionBadge` with `.impossible` renders its lock variant ("Locked until 20:00"), which is what the real row shows under that mode.
- *Popover width.* The sheet is 560 wide including its own padding; the popover content is 600 so the sheet sits inside the popover's 20-pt padding.
- *Escape hatch.* The sheet has only Done (disabled until step 1 is green), as the spec says; a "Not now" would be undone by the next `didBecomeActive` anyway. The app can still be quit from the menu bar.
- *Version.* No bump: app-only change, the daemon binary is unchanged, so `needsUpdate` stays false. (chrome-pages bumps to 0.6.0 on its own.)
